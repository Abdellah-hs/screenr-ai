Screenr AI | Weekly Changelog – April 13 – April 17, 2026

✨ Features

• **Canonical Application State Machine**: Established the strict ATS state machine described in CLAUDE.md. Replaced the legacy `screening / screening_q / interview` triplet with the full canonical set (`screening_review_pending`, `screening_approved`, `screening_sent`, `screening_completed`, `screening_scored`, `interview_scheduling`, `interview_scheduled`, `interview_completed`, `interview_scored`, `reference_check`, `final_interview_scheduling`, `archived`) on `candidate_stage_enum`. `APPLICATION_STATE_TRANSITIONS` in `src/lib/constants.ts` was rewritten in lockstep so every legal edge is enumerated in one place. (`supabase/migrations/20260418000000_expand_candidate_stage_enum.sql`)
• **Append-Only Transitions Log + Atomic RPC**: New `application_transitions` table records every state change with `{from_state, to_state, actor (system|ai|recruiter), rationale, timestamp}`. The `transition_application` Postgres RPC validates the edge, appends the log row, and updates the application's status atomically — making illegal transitions impossible at the database boundary, not just the application layer. (`supabase/migrations/20260417000000_application_transitions_log.sql`, `src/lib/data/transitions.ts`)
• **Split Resume Scoring from Decisioning**: `scoreApplicationResume()` now produces evidence only (score + rationale + factors persisted to `ai_audit`); the new `evaluateResumeScoringOutcome()` is the rule layer that reads the score and calls `transition()` with the correct target state. HITL mode routes to `screening_review_pending`; auto mode routes to `screening_approved` or `screening_rejected` based on threshold. (`src/lib/actions/candidates.ts`)
• **Screening Send/Score Wired Into Transitions**: `buildAndSendOne` in `src/lib/actions/screening-questions.ts` now emits `screening_sent` after the candidate response row is seeded. `scoreScreeningAnswers` emits `screening_sent → screening_completed` before the AI call and `screening_completed → screening_scored` (actor `ai`) after `saveAnswerScores`. The state changes are idempotent thanks to the RPC's same-state guard. (`src/lib/actions/screening-questions.ts`, `src/lib/actions/respond.ts`)
• **Failure States as First-Class Citizens**: Added explicit failure states (`screening_expired`, `interview_no_show`, `processing_failed`) to `candidate_stage_enum` and `APPLICATION_STATE_TRANSITIONS` so error paths are observable, not silent. `getCandidateScreeningState` lazily emits `screening_expired` and flips the response row to `expired` the first time a recruiter opens a candidate past the response deadline (no cron required — the authed read is the trigger). (`supabase/migrations/20260419000000_failure_states.sql`, `src/lib/data/screening-questions.ts`)

🔒 Security / Correctness

• **Database-Enforced State Transitions**: With `transition_application` doing the validation, no Server Action can accidentally write `.update({ status: X })` to bypass the rules — illegal transitions are rejected at the RPC boundary even if a future caller forgets to use `transitionApplication()`. The auth check inside the RPC also requires `auth.uid()` to match the campaign owner, preventing a logged-in recruiter from mutating another recruiter's pipeline.
• **Append-Only Audit Trail**: The transitions log is append-only by design — there are no `UPDATE` paths. Every state change is permanently attributable to a `system`, `ai`, or `recruiter` actor with a rationale string, which is the substrate the PRD's manual-override and disposition-code rules depend on.

🐛 Bug Fixes

• **`updateApplicationStage` and `advanceApplicationStatus` no longer write `status` directly**: Both helpers now delegate to `transitionApplication()` in `src/lib/data/transitions.ts`. There are no remaining direct `.update({ status: ... })` calls on the applications table.
• **HITL branch was silently leaving applications in `new`**: `evaluateResumeScoringOutcome` previously took no action in HITL mode, leaving recruiter-review applications stuck at `new`. It now transitions `new → screening_review_pending` so the review queue is observable.
