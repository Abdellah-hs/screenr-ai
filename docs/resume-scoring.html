Screenr AI · Resume stage

Evidence to Threshold

How a CV becomes a gate result and a ranking number — every step from the document the model is shown to the transition the state machine records.

The model never returns a number. It reads the CV and reports, per criterion, how strongly the document evidences it — plus the exact words it read that from. Every figure after that is arithmetic in code, from a fixed table. Change the number and you must change the reading, not the maths.

The six stages

The rail on the left says who is acting. Indigo is the model producing evidence; ink is deterministic code. There is exactly one place where the colour changes, and nothing after it consults the model again.

01
Code

Build one document

The parsed CV fields are flattened into readable sections — name, headline, summary, skills, experience, education. At apply time the original extracted text is appended verbatim, so quotes can be checked against the real file rather than a model's reading of it. Over 70,000 characters, the middle is dropped and marked.

That one string is used for three things that must agree: what the model is shown, what its quotes are verified against, and what the cache key hashes. If they could differ, quote-checking would be theatre — the model could quote something real from a document the validator never saw.

Inparsed CV + raw text Outnormalized document
02
Model

Read the document, report evidence

gpt-4o-mini, temperature 0, seed 7, structured outputs. It receives the job description as context, the criteria as a bare numbered list, and the document. For each criterion, in the same order, it must return an evidence level, the verbatim quotes it read that from, which section each came from, and a duration only if the CV literally states one.

Two things are withheld deliberately. It is never told which criteria are must-haves — knowing a criterion is a knockout gives it reason to shade evidence toward a verdict it can guess at. And borderline always takes the lower level.

Indocument + criteria Outlevel + quotes, per criterion
The model stops here
03
Code

Verify every quote

This is where the model stops being trusted. Two failure types are kept apart because they mean different things:

Structural — wrong number of criteria, or wrong order — throws and rejects the whole run. Nothing can be aligned, so nothing is safe to salvage. Evidential — a quote is not in the document — discards that quote with a warning. A criterion left with no verified quote is downgraded to unclear, which scores zero.

Matching ignores only cosmetic differences: case, curly versus straight quotes, dash types, whitespace. It can widen a match, never invent one. Validation can only lower a level, never raise one.

Inreported evidence Outverified evidence + warnings
04
Code

Level becomes a number

A lookup, not a judgement. The same table serves the voice-screening stage, so a strong reading is worth 80 wherever it was read — a recruiter comparing two stage scores is comparing two numbers made the same way.

Inevidence level Out0 – 100 per criterion
05
Code

The gate, then the ranking

The gate runs first. Every must-have is checked on its own against a fixed 60. All must pass; every failure is reported, not just the first. There is no total across must-haves and there cannot be — the moment you sum them, a surplus on one pays for a shortfall on another and "must" quietly becomes "mostly".

Then, only for an eligible candidate, the ranking: the mean evidence score across every criterion, must-haves included, rounded. An ineligible candidate has no ranking at all — never a low number, which would read as "how close they came" and invite an argument with the gate.

Inscored criteria Outeligible? + ranking or null
06
Code

A rule decides, the state machine moves

The scorer never transitions. It hands the result to a pure rule, which returns a target state and a written rationale; the caller executes it. The threshold is consulted here and nowhere else.

Inresult + campaign config Outtransition + rationale

The evidence ladder

Six levels, fixed meanings, fixed scores. This is the seam where the AI stops and the machine starts: the model chose a label, and every number after that point is a consequence of that label and nothing else.

Level What it means on a CV Score
not_present No explicit evidence of the criterion appears in the resume. 0
unclear Wording that may relate to the criterion, but too ambiguous or indirect to establish that it is actually met. Also where an unverifiable quote lands. 0
weak Explicitly mentioned (a skills list, say) with zero concrete examples — no project, responsibility, task, outcome or duration stated. 25
partial 1 concrete example of limited exposure: a course, small project, isolated task, or short-term use (<3 months). Some actual exposure, not sustained professional use. 55
strong 1–2 clear examples of meaningful professional use: concrete projects or roles with specific responsibilities, repeated use, measurable outcomes, or duration ≥3 months. 80
very_strong 3+ substantial examples, or 2+ showing ownership, leadership, architecture decisions, or long-term professional experience (≥12 months). 100
Why unclear scores zero

"We could not tell" is not partial credit. It sits beside not_present on the ladder but says something different in the record: not_present asserts the CV contains no such evidence, which we did not establish — we established that the quote could not be found.

These definitions are the scoring rule

They are pasted into the system prompt verbatim, so the boundary between strong and very_strong is exactly the sentence above and nothing else. Rewritten on 23 Aug 2026 to count examples and name duration floors rather than lean on "meaningful" and "substantial" — two readers should reach the same level from the same CV, and an adjective is not a test. Editing them means bumping the prompt version, which invalidates every cached reading rather than answering the old question.

What the model may and may not say

The boundary is enforced in the prompt and again in the schema. There is no field for a verdict, so there is nowhere to put one.

  • May: report an evidence level, quote the document verbatim, name the section a quote came from, explain why it counts, and read a duration the CV states outright.
  • May not: return a numeric score, a weight, an overall rating, a tier, an eligibility verdict, a ranking, or a hire / no-hire recommendation — in any field, including free-text notes. Doing so is an error even when confident.
  • May not: infer a skill from a related one. React is not proof of Next.js. JavaScript is not proof of TypeScript. "Familiar with frontend" is not proof of a framework.
  • May not: be told which criteria are must-haves. Priority is stripped before the prompt is built.

The invariant

A nice-to-have can never repair a failed must-have — not by weighting, averaging, or any other route. Eligibility is decided before any averaging happens, and an ineligible candidate has no ranking for a surplus to inflate. This is the property the whole module exists to hold, and the tests assert it directly.

Two bars, and only one is yours

Both are pass marks on the resume stage, and they are constantly confused because only one of them is ever visible on a scored CV.

Bar Value Applied to Set where
Must-have minimum 60 Each must-have criterion, on its own. All must clear it. Fixed in code, same on every campaign
Resume threshold 70 The ranking score, once the candidate is already eligible. Your campaign settings

They cannot share a line. A must-have is a gate — the CV either states the qualification or it does not — while the ranking orders the candidates who already passed. At 60, partial fails and strong passes: a must-have needs concrete professional or project evidence, not a mention and not one course.

What the rule does with them

Situation Mode Transition
Any must-have failed either rejected · disposition LOW_SCORE
Eligible human_in_loop screening_review_pending — the threshold rejects nobody here; it only sorts your queue
Eligible, ranking ≥ threshold fully_auto screening_approved
Eligible, ranking < threshold fully_auto rejected · disposition LOW_SCORE
Read the threshold against your rubric, not as a grade

The ranking is a mean over every criterion you wrote down. Add four nice-to-haves that most CVs will not evidence and you pull every candidate's ranking down by design — the number is honest, but 70 then means something much stricter than it looks. If something genuinely matters, make it a must-have: that is the control that actually gates, and it now lifts the ranking too.

What gets written down

AI output is evidence, not truth, so the whole run is recoverable after the fact — including what was corrected on the way through.

Where What
The application row Ranking score (null when ineligible), the eligible flag, the full evaluation, tier, the written rationale, rubric version, and scored_at — which is the "has this been evaluated" marker, not the score.
The audit log Raw model output, model name, prompt version, scoring-rules version, rubric version, the document hash, the criteria and their priorities, every validation warning, whether the evidence was cached, and where the run came from.
The evidence cache Keyed on the document hash, the criteria labels and priorities in order, rubric version, prompt version, model, and rules version. Only the evidence is cached — the score is recomputed on every run, so a served result can never predate the rules it claims to follow.

Criterion ids are deliberately left out of the cache key: re-saving a rubric mints new ids for unchanged criteria, and keying on them would throw away every cached result each time you edited an unrelated field. What identifies a criterion is its label, its priority, and its position — the three things the prompt actually depends on.
