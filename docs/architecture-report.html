1. Executive Summary

Screenr AI is an internal Applicant Tracking System and AI-assisted interview platform. This report documents the system as it exists today: its layered architecture, the state machine that governs every candidate movement, the end-to-end workflow from inbox to hiring decision, and the deltas between the current implementation and the product requirements document.

The system is built on a strict architectural principle: Control > AI > Data. Application state is governed by explicit rules and a single transition function. Artificial intelligence produces scores, classifications, and written evidence, but it never mutates state directly. Every status change — whether originated by a background rule, a scoring threshold, or a recruiter's manual override — passes through one code path, one database RPC, and one append-only log.

Recent work has landed the foundation for that discipline: a centralised transitionApplication() entry point, an append-only application_transitions audit table, an atomic database RPC that enforces ownership and concurrency, and a clean split between the AI scoring function and the rule-based advancement function. Several gaps versus the product requirements remain, the largest being the migration from text-based screening answers to PRD-mandated video/audio recordings and the expansion of the stage enum to cover scheduling, reference checks, and final interview scheduling.

2. Architectural Overview

2.1 The three-layer pattern

All data flow in the application goes through three clearly bounded layers. Upper layers may call lower layers; the reverse is forbidden.

LayerLocationResponsibilityForbidden from
Server Actions src/lib/actions/ Entry point for reads/mutations from React. Auth guard, Zod validation, rate limiting, orchestration of services and data-layer calls, final revalidatePath(). —
Services src/lib/services/ Third-party integrations: OpenAI, Gmail, PDF parsing, email delivery. Encapsulates all provider-specific code. Must not read user session; receives scoped inputs only.
Data src/lib/data/ Pure Supabase queries and mutations. Returns raw shapes. transitions.ts is the sole entry point for status mutations. No auth checks, no Zod validation, no AI calls.

2.2 The control-flow invariant

The single most important property of the system is this: every write to applications.status funnels through one function. That function calls one RPC, which writes one log row, atomically with the status update. The codebase contains no direct .update({ status }) calls outside that path, which can be verified by grep.

Consequence. The transition log is the authoritative history of every application. Querying application_transitions ordered by created_at reconstructs every movement, actor, timestamp, and rationale for any candidate. There is no way to mutate state without leaving a trace.

2.3 Security model

  • Middleware (src/middleware.ts) redirects unauthenticated requests away from the dashboard.
  • Server actions re-check supabase.auth.getUser() and validate UUIDs before any work.
  • Row-level security is enabled on all pipeline tables; campaign ownership is enforced at the database.
  • The transition RPC runs as SECURITY DEFINER but checks auth.uid() itself against campaigns.user_id — defense in depth.
  • Resumes are stored in a private Supabase Storage bucket; access is via one-hour signed URLs.

3. The ATS State Machine

3.1 Entities

  • Candidate — a person. Stable across campaigns. Holds identity data only.
  • Campaign — a hiring process for one role.
  • Application — the pairing of a candidate with a campaign. All pipeline state, timestamps, scores, decisions, and transitions live on the application, never on the candidate. One candidate may have many applications.

3.2 The current transition map

Legal transitions are declared in src/lib/constants.ts and enforced both in TypeScript and at the database:

new           → screening, screening_q, rejected, withdrawn
screening     → screening_q, rejected, withdrawn
screening_q   → interview, rejected, withdrawn
interview     → manager_review, rejected, withdrawn
manager_review → hired, rejected, withdrawn
rejected / hired / withdrawn → [ ]   (terminal)

3.3 The transition function

The TypeScript entry point transitionApplication() performs:

  1. Actor validation — recruiter transitions require a written rationale.
  2. Auth check — supabase.auth.getUser() or reject.
  3. Pre-flight fetch of current status for a readable error on illegal transitions.
  4. Idempotent no-op if from === to.
  5. TS-side legality check against APPLICATION_STATE_TRANSITIONS.
  6. Call to the transition_application RPC.

3.4 The database RPC

The RPC is SECURITY DEFINER plpgsql. Its body is a single transaction:

1. SELECT ... FOR UPDATE   -- locks the row; concurrent callers block
2. ownership check against auth.uid()
3. idempotency check
4. UPDATE applications SET status = new
       WHERE id = $1 AND status = from_state   -- concurrency guard
5. INSERT INTO application_transitions (...)

Any failure rolls back all five steps. The WHERE status = from_state clause on the UPDATE is the concurrency guard: if another caller won the race, ROW_COUNT is zero and the function raises "Concurrent state change".

3.5 Append-only audit table

The application_transitions table has:

  • RLS SELECT policy scoped to campaign owners.
  • No INSERT, UPDATE, or DELETE policies — only the SECURITY DEFINER function can write, and nothing can delete.
  • Columns: id, application_id, from_state, to_state, actor (system / ai / recruiter), rationale, created_at.

4. End-to-End Candidate Workflow

4.1 Phase 1 — Resume intake (Gmail → new)

Entry point: syncResumesFromGmail() in src/lib/actions/candidates.ts, invoked from the "Sync Gmail" button on a campaign detail page.

  1. Guards. Auth check; rate limit of 5 syncs per 10 minutes per user.
  2. Inbox scan. Up to 5 unread messages with PDF attachments are fetched from the campaign's configured Gmail inbox.
  3. Storage. The PDF is uploaded to Supabase Storage. The path (not a public URL) is stored on the application — resumes are private and accessed via one-hour signed URLs.
  4. Extraction. pdf-parse converts the PDF to text locally. The text is sent to OpenAI with a structured schema, returning typed JSON (name, email, phone, links, skills, experience, education).
  5. Candidate upsert. Keyed by email. An existing row is updated; a new email creates a new candidate record.
  6. Application create / resubmit. On first apply, an application row is inserted in status new. On a resubmission, the resume and parsed data are overwritten; recruiter-owned fields (status, score, rationale) are preserved and a breadcrumb is written to the AI audit log.
  7. AI audit row. Every AI extraction is logged with model version, prompt version, input snapshot, and raw output.
  8. Score attempt. If the campaign has scoring criteria configured, the resume is scored and the rule layer decides whether to advance. Scoring failures are non-blocking.
  9. Mark read. Only after all of the above succeed is the Gmail message marked read.

4.2 Phase 2 — Resume scoring (split: AI → evidence, rule → decision)

The scoring pipeline is split into two functions to enforce the AI/rule boundary in code.

AI layer — scoreApplicationResume()

  • Fetches the campaign scoring config.
  • If no criteria are configured, returns null — scoring is optional.
  • Calls OpenAI with the parsed resume, screening criteria, and job description.
  • Receives { overall_score, tier, rationale, factors }.
  • Persists all of that on the applications row as evidence.
  • Never touches status. Returns the result for the rule layer to consume.

Rule layer — evaluateResumeScoringOutcome()

  • Does not call AI. Does not query the database for the config — the AI layer passes it in.
  • In fully_auto mode: score at or above threshold transitions to screening_q; below threshold transitions to rejected.
  • In human_in_loop mode: no transition — the application remains in new until a recruiter acts. (This is a legacy shortcut; the target state is screening_review_pending, blocked on an enum migration.)
  • Each transition carries a rationale string recording the score and threshold.

4.3 Phase 3 — Screening questions (current text flow)

Applications that reached screening_q are eligible to receive screening questions.

  • Eligibility filter. The bulk-send flow queries applications with status = 'screening_q', a non-null resume_score, and an email on file.
  • Question bank. Questions per campaign live in screening_questions; regeneration wipes and re-inserts.
  • Response lifecycle. A separate table, screening_question_responses, carries its own status (pending → sent → responded → scored → expired). This is distinct from the application's status — the application only advances when the rule layer reads the overall score.
  • Candidate experience. Public, token-based pages (no login) where candidates submit answers; token is validated server-side.
  • AI scoring. On submission, AI produces per-answer scores and an overall score, all written back to the response row.
  • Transition. A rule layer reads the overall score and calls transitionApplication() with interview or rejected.
PRD gap. The current flow treats screening answers as text. PRD 3.4.3 requires video/audio recordings with a practice question, re-recording, and transcript-linked scoring evidence. This is the largest functional gap in the system and will require recording storage, a transcription service, and a scoring model that references transcript excerpts.

4.4 Phase 4 — Interview, manager review, terminal states

From screening_q, the legal onward move is interview, which today is recruiter-driven via updateCandidateStage(). From interview, the legal moves are manager_review, rejected, or withdrawn. From manager_review, the legal moves are hired, rejected, or withdrawn. All three terminal states have empty transition arrays — the RPC will reject any further movement.

PRD gaps. The current pipeline compresses too much into the interview stage and skips several PRD-mandated phases:
  • No distinct interview_scheduling / interview_scheduled / interview_completed / interview_scored states.
  • No optional reference_check stage between interview scoring and manager review.
  • No final_interview_scheduling after manager review for the human final interview.
  • No distinct archived terminal state.
All of these require a database enum migration and corresponding rule-layer handlers. The transition plumbing is ready.

5. The Transition Machinery in Detail

5.1 Call graph

React component
  │
  ▼

  │
  ▼
advanceApplicationStatus (system)  or  updateApplicationStage (recruiter)
  │
  ▼

  │   (legality check, rationale check, actor check)

  ▼

5.2 Properties the machinery guarantees

PropertyHow it is enforced
No silent state change Direct .update({ status }) does not exist in the codebase; the only writer is the RPC. Grep catches regressions.
Atomicity RPC is a single plpgsql transaction. Either status change and log row both happen, or neither.
Concurrency safety SELECT ... FOR UPDATE locks the row; the WHERE status = from_state guard on the update causes the loser of a race to raise.
Tenant isolation The RPC re-checks auth.uid() against campaigns.user_id, bypassable only by a privileged service role.
Recruiter accountability TS guard in transitionApplication() rejects recruiter transitions without a rationale.
Append-only audit RLS exposes no INSERT/UPDATE/DELETE policies on application_transitions; only the SECURITY DEFINER function can write.

8. Recommended Roadmap

  1. Stage enum expansion. A single Supabase migration adds the canonical values to candidate_stage_enum. APPLICATION_STATE_TRANSITIONS is updated in the same pull request. This is purely data; behaviour only changes when rule handlers reference the new states. Unblocks the HITL fix and every downstream stage.
  2. HITL branch. Once the enum exists, change evaluateResumeScoringOutcome to transition HITL applications to screening_review_pending. Add a recruiter-facing review queue.
  3. Screening recording pipeline. Add a storage bucket for recordings, a transcription service call, a screening_recordings table, and a scoring model that emits transcript excerpts. Migrate the public candidate page from text fields to a recording UI with practice question and re-record. Largest single piece of work.
  4. Interview scheduling. Introduce the four post-screening states, build a candidate self-serve calendar page, and wire the confirmation/reminder emails.
  5. Reference check. Optional stage between interview_scored and manager_review. First-class in the transitions map, gated by a campaign setting.
  6. Final interview scheduling. Calendar integration for the human final interview after manager_review.
  7. Deduplication policy. Change upsertCandidate to detect potential duplicates on email / phone / profile similarity and flag them, rather than silently merging.
  8. Archived terminal state. For campaigns that close without a hire or where an application should be removed from active metrics without a harsh "rejected" label.
