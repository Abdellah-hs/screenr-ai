Screenr AI | Weekly Changelog – April 20 – April 24, 2026

✨ Features
• **Decoupled Rules Layer**: New `src/lib/rules/` directory holds pure decision functions — read already-validated evidence (an AI score, a response status), return a `TransitionDescriptor` or guard error, and never touch Supabase / `revalidatePath` / `redirect`. Documented in `src/lib/rules/README.md`. The reference implementation `evaluateResumeScoringOutcome` (resume scoring) was moved here and converted to descriptor style. This is the architectural layer that implements "Control > AI > Data" — AI produces evidence, rules decide. (`src/lib/rules/README.md`, `src/lib/rules/resume-scoring.ts`)
• **Screening-Response Guards Extracted**: `assertResponseIsOpen`, `assertResponseNotResubmitted`, and `validateRequiredAnswersPresent` were lifted out of `src/lib/actions/respond.ts` into `src/lib/rules/screening-response.ts` with a dedicated `ScreeningResponseError` subclass so candidate-facing message strings stay byte-stable (the public form surfaces them verbatim and tests pin them). The action is now a thin orchestrator: token verify → load → guard → save. Shipped as PR #21 (squash-merged to main). (`src/lib/rules/screening-response.ts`, `src/lib/actions/respond.ts`)
• **Screening Lifecycle Wired Into State Machine**: Sending screening questions transitions the application to `screening_sent`; candidate submission transitions it to `screening_completed`; AI scoring transitions it to `screening_scored`. Previously the response row had its own `pending | sent | responded | scored` lifecycle but the application's status sat motionless — now the audit log records every step. All three are best-effort: the side effect (email / answer save / score persist) commits first, then the transition runs and is logged on failure so a transient RPC error can't ghost an email or lose a candidate's submission. (`src/lib/actions/screening-questions.ts`, `src/lib/actions/respond.ts`)
• **Threshold-Based Branching for Screening Scoring**: `evaluateScreeningScoringOutcome` now reads campaign config (`automation_mode` + `screening_threshold`) and returns an ordered chain of transitions, parallel to `evaluateResumeScoringOutcome`. HITL rests at `screening_scored`; `fully_auto` chains `screening_scored → interview_scheduling` on a pass and `screening_scored → rejected` on a fail (boundary score equals threshold counts as pass). The action loops the chain and stops on the first transition error so it can't try an illegal step from a stuck source state. (`src/lib/rules/screening-response.ts`, `src/lib/actions/screening-questions.ts`)
• **`requireUserId()` Auth Guard Helper**: New `src/lib/auth/guards.ts` wraps `supabase.auth.getUser()` and throws `Unauthorized` on no session. Centralises the action-layer auth pattern; existing actions can migrate from the inline `getUser()` boilerplate incrementally. (`src/lib/auth/guards.ts`)

🛠️ Improvements
• **Layered Architecture Documented**: `CLAUDE.md` updated to reflect the four-layer pattern (Server Actions → Rules → Data → Services) with explicit boundaries — rules forbid Supabase imports, data layer performs no auth checks, all `applications.status` writes go through `transitionApplication()`. Compliance status section reorganised: lifecycle-wiring and rule-branching items moved from "Open violations" to "Completed". (`CLAUDE.md`, `src/lib/rules/README.md`)
• **Test Coverage for the New Rules**: `src/lib/rules/screening-response.test.ts` exercises the three guards (load-path, submit-path, required-answer presence) plus the new `evaluateScreeningScoringOutcome` branching matrix (HITL rests, auto-pass advances, auto-fail rejects, boundary inclusive). All 49 tests pass; no I/O, no mocks — rules are pure so the test inputs and outputs are the whole story.
• **Token-Based Candidate Reads**: `fetchApplicationForResponse` and `fetchApplicationCampaignId` added to `src/lib/data/candidates.ts` for the public `/respond/[token]` page. Unauthenticated reads gated by signed token verification (not RLS), matching PRD "Candidate-Facing Constraints" — candidate pages are token-based, never account-based. (`src/lib/data/candidates.ts`)
• **Per-Action Ownership Helper**: `verifyCampaignOwnership(campaignId, userId)` added to `src/lib/data/campaigns.ts` for actions that need to gate recruiter-scoped operations without re-fetching the full campaign aggregate.

🔒 Security / Correctness

• **AI Stays Advisory, Never Authoritative**: With the rules layer in place, the AI scoring path is now explicitly two-step everywhere: `score*` produces evidence (persisted to `ai_audit`), then a pure `evaluate*` rule reads that evidence and returns a transition descriptor. No AI output ever flows directly into a `status` write — the rule decides, the action executes via `transitionApplication`. This closes the gap CLAUDE.md flags as the #1 anti-pattern.
• **Audit Log Granularity**: For an auto-passing candidate, the screening flow now writes two transition rows (`screening_completed → screening_scored` with the score, `screening_scored → interview_scheduling` with the rationale) instead of one. The intermediate row makes "the AI scored this candidate" greppable in the audit log even when auto-mode advances past it instantly.

🐛 Bug Fixes

• **Lifecycle Transitions Were Missing**: Sending screening questions, candidate submission, and AI scoring previously left the application's `status` untouched while only the response row's status moved. The state machine and the response lifecycle were silently out of sync — now wired end-to-end.
